The mental model

Every workflow is three parts. Nothing more.

You start with something (an email, a meeting, a question). Fluso runs steps across your apps. You end with something useful (a summary, a draft, a decision). That is a workflow.

How it works

Connect. Say. Review.

Fluso is reactive. It does not run on its own. You trigger every workflow with a message or a command. Fluso does the work, then shows you the result for approval.

01

Connect your apps

Link Gmail, Slack, Linear, Calendar, Google Drive, GitHub, and 100+ other tools. Review per-tool permissions. You decide what Fluso can read and what it can write.

02

Say what you need

Type a sentence. Pick a workflow from the library. Or describe your own and let the builder draft a prompt. One message triggers the whole chain.

03

Review and approve

Fluso shows you the result. Drafts before sending. Issues before creating. Posts before publishing. You stay in control of everything that goes out.

Where you stay in control

Fluso reads your data to understand context, but every outbound action (sending an email, posting a message, creating an issue, publishing a post) requires your explicit approval. Nothing leaves your accounts without you saying yes. This is not a setting. It is how Fluso works by design.

Custom MCP servers

Need a tool that is not in the catalog? Connect it as an MCP server. Anything that speaks the Model Context Protocol works. A team private MCP, a smaller SaaS that shipped an MCP endpoint, a new tool a developer built over the weekend. Paste the URL, sign in, use the tools.

If a service is both a connector and an MCP server, Fluso uses the MCP server first and falls back to the connector only if the MCP cannot satisfy the request.
